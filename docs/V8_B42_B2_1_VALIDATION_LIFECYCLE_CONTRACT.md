## Existing boundary and compatibility

Inspected sources (implementation takes precedence over older reports):

- [B4.2 integrity migration](../supabase/migrations/20261008000000_qualified_evidence_integrity.sql), [whole-row v2 migration](../supabase/migrations/20261008010000_qualified_evidence_snapshot_v2.sql), and [integrity review](V8_B42_QUALIFIED_EVIDENCE_INTEGRITY.md).
- [Trusted reader](../lib/validation/promotion/trusted-qualified-evidence-reader.ts), [promotion service](../lib/validation/promotion/promotion-service.ts), [Validation HTTP authentication](../lib/validation/server/http.ts), [command service](../lib/validation/server/service.ts), and [user capabilities](../lib/auth/user-capabilities.ts).

B3.1 atomically writes a sanitized shared observation and private final ledger; B4.2 adds an immutable attestation of the actual persisted whole row. Finality is a non-null result link, not a lifecycle status. Ledger and snapshot runtime access is SELECT-only for `service_role`; attested shared rows reject UPDATE/DELETE. Existing `supersedes_promotion_id` and `deactivation_reason` do not implement correction: the reader supports only null values and final-source/group uniqueness prevents simple replacement.

The reader recomputes the B3.1 fingerprint, verifies native v2 whole-row integrity, and returns eight allowlisted fields for one exact canonical UUID. Incomplete candidate reads and missing/corrupt/unsupported integrity for qualifying historical records fail the entire read generically. It does not check current canonical status or provide lifecycle filtering. This document must not be read as evidence that withdrawal, revocation, reconciliation, or erasure already works.

Preserve Discovery ingestion, Validation qualification and representative ranking, Data Moat integrity, canonical bootstrap, existing retry behavior, and all three polarities. No Knowledge Evolution connection, historical backfill, production/staging change, or lifecycle command belongs to this PR.

## Historical proof and current eligibility

Keep historical qualification/integrity proof separate from a future private, append-only lifecycle event stream and its current eligibility projection. Never UPDATE an old ledger, shared row, snapshot, fingerprint, or classification to express a lifecycle change. A valid attestation proves persisted integrity under a versioned contract; it does not prove that a trusted caller selected the correct canonical or that continued use remains authorized.

Only `active` evidence may contribute to current qualified reads or counts. Active requires valid supported historical proof, unambiguous lifecycle authority, and a currently permitted exact canonical identity. An intact historical record in any other state contributes zero current evidence. Historical audit access is separately authorized; it is not the current reader or a public export.

A future reader must evaluate lifecycle and integrity in one consistent PostgreSQL/PostgREST snapshot. Missing, conflicting, stale, malformed, or unsupported lifecycle authority fails closed; do not silently infer active or return a partial complete result. Deliberately excluded non-active records require valid exclusion authority; they must not conceal corruption of an otherwise eligible record. Historical rows need an explicit reviewed compatibility policy, not automatic re-attestation or default activation. Until that is implemented, retain the existing reader behavior and keep new consumers disconnected.

## States

These are conceptual labels, not proposed SQL identifiers or changes to the existing ledger.

| State                  | Meaning and current use                                                                                                                                                |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| active                 | Qualified, intact, authorized for current use; eligible.                                                                                                               |
| suspended              | Temporary authorized hold for a specific concern; ineligible until explicitly cleared.                                                                                 |
| withdrawn              | Verified owner withdrew shared use; historical qualification is not declared false; ineligible.                                                                        |
| revoked                | Independently authorized administrative decision invalidates permission or trust; ineligible.                                                                          |
| superseded             | A separately qualified replacement has committed and is linked; old record is ineligible.                                                                              |
| pending reconciliation | Canonical or lifecycle authority cannot safely determine eligibility; ineligible. This label does not excuse missing integrity.                                        |
| privacy-erased         | Authorized deletion has removed covered content and identifying links, including duplicate proof copies; terminal and ineligible. Only approved minimal audit remains. |

## Transition and authorization contract

Deny every transition absent from this table. Repeating an identical committed command is an idempotent acknowledgement, not another transition. No command may weaken an existing restriction. Privacy-erased is terminal. Revoked and superseded never return to active; withdrawn does not reactivate in place. Any later contribution needs fresh consent and separately qualified new evidence, subject to revocation and privacy restrictions.

| From                                                             | To                     | Required authority and preconditions                                                                                                                                                                                                                                                     |
| ---------------------------------------------------------------- | ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| No final evidence                                                | active                 | Existing controlled promotion authority plus a future atomic initial lifecycle event; complete qualification and attestation. No new promotion path here.                                                                                                                                |
| active                                                           | suspended              | Independently authorized evidence administrator, scoped reason and case reference; no owner impersonation.                                                                                                                                                                               |
| active, suspended                                                | pending reconciliation | Trusted server detection of persisted canonical change/authority ambiguity, or scoped administrator; deterministic reason. Detection can only restrict use.                                                                                                                              |
| pending reconciliation                                           | suspended              | Scoped administrator records an unresolved hold; cannot resolve identity by assertion.                                                                                                                                                                                                   |
| suspended, pending reconciliation                                | active                 | Scoped administrator explicitly clears the recorded restriction, with fresh integrity, canonical, consent and lifecycle checks; no intervening withdrawal, revocation, replacement or erasure.                                                                                           |
| active, suspended, pending reconciliation                        | withdrawn              | Authenticated owner verified against persisted lineage in the transaction; no other owner's data affected.                                                                                                                                                                               |
| active, suspended, pending reconciliation, withdrawn, superseded | revoked                | Independent scoped administrative authorization, recorded rationale and case; owner consent is neither required nor a substitute. Preserve prior withdrawal/replacement events.                                                                                                          |
| active, suspended, pending reconciliation, withdrawn             | superseded             | Owner-authorized correction plus separately verified replacement qualification, consent and canonical authority; administrative clearance of any hold is additionally required. Atomic replacement linkage and exclusion of predecessor; never bypass a withdrawal with implied consent. |
| Any state except privacy-erased                                  | privacy-erased         | Dedicated, independently authorized privacy executor after verified request/legal basis and approved retention/hold decision; an owner may request deletion but cannot grant this execution authority.                                                                                   |

Administrative authority must be independent of the evidence owner's claim and of possession of the application credential. A scoped server-verified grant must bind a verified actor to an operation, target, purpose, expiration and authorization decision reference. Recheck it at execution; record actor, executor and authorizer distinctly. Grant issuance, self-approval constraints and any two-person approval requirement remain security decisions below. Until those are defined, administrative transitions are disabled, not implicitly permitted.

Reject caller-supplied owner IDs, role strings, canonical choices, grant claims, or boolean approval flags as authority. Owner withdrawal should follow `requireUser` and persisted owner scoping, with a database boundary that cannot accept a forged owner via the service credential alone. Cross-owner/not-found responses must not reveal existence. Withdrawal is not revocation or deletion and must not erase a contradicting result to improve reported validation.

### Why service_role and internal_test are insufficient

`service_role` is a technical executor with broad access, not an independently authenticated administrator. Existing promotion SQL checks persisted lineage and freshness, but trusts TypeScript for representative ranking, exact resolution and fingerprint construction. A service credential holder can bypass that preparation through the allowed RPC. Snapshot integrity does not repair that semantic trust limitation. A future administrative RPC granted to `service_role` without independently verifiable scoped authorization would repeat that gap; an actor ID parameter or mutable session GUC is insufficient.

The code's actual entitlement is `internal_tester` (sometimes called `internal_test` in task discussions), with `unlimitedScans`. It grants scan capability, not revocation, erasure, consent, or administrative access to other owners' evidence. Neither entitlement, application metadata, UI visibility, nor RLS bypass establishes administrative authorization. Database owners can alter guards; this contract does not claim protection against a database administrator controlling schema and proofs.

## Correction, replacement and polarity

Correct private source material through versioned source/classification records and a new human-approved shareable statement. Re-run qualification, exact canonical resolution, representative selection and supported attestation for a new promotion. Link predecessor and successor using a reviewed replacement contract; do not reuse a fingerprint to relabel old evidence. Existing final-source/group indexes and supersedes FK semantics require explicit additive design before this can work; changing policy version to evade uniqueness is forbidden.

Replacement creation, lifecycle events and predecessor exclusion commit atomically or all roll back. Competing replacements have one winner; no cycles, branching successors or duplicate active contribution. Retries of the original B3.1 promotion remain duplicates and must never restore eligibility or manufacture historical snapshots. A revoked record cannot be laundered through replacement; any remediation requires separate security review.

Supporting, contradicting and mixed remain first-class persisted polarity. Lifecycle decisions cannot depend on whether evidence is favorable. Corrections may change polarity only in the new human-authorized evidence; retain the old polarity in historical proof, subject to privacy deletion. Never silently coerce mixed to supporting or remove contradiction from current counts without a valid lifecycle reason.

## Canonical merges and deprecated identities

Retain the exact historical canonical UUID, title, fingerprint and composite FK in the old proof. Do not rewrite an attested row, follow aliases during read, or silently aggregate old evidence into a merge target. A deprecated, merged, missing or ambiguous current identity excludes evidence through pending reconciliation in the future contract. Prevent a read/merge race through the same consistent authority snapshot; a background reconciliation delay must not allow stale active eligibility.

Reconciliation needs explicit persisted merge provenance and fresh exact authority checks. A renamed title alone must not imply a merge. If identity remains the same and valid, an authorized clearance can restore eligibility without rewriting historical display fields. A different canonical UUID needs a separately qualified replacement and lineage review, including participant independence and duplicate counting across merged groups. An alias or active target alone is insufficient. Preserve the existing canonical-registry -> sorted experiments -> participant -> representative-group lock order; lifecycle coordination must extend it consistently, never invert it or change bootstrap behavior in this documentation PR.

## Privacy deletion and minimum audit

Immutability is the ordinary integrity rule, not a reason to retain personal data indefinitely. Privacy erasure is a separately reviewed destructive exception, not a general UPDATE/DELETE escape hatch or administrative revocation. Current guards and restrictive FKs intentionally block it today. Do not disable triggers, weaken all runtime grants, or call a service-role delete and claim compliance.

Before implementation, inventory private interviews/participants, approved statements, shared observations, ledger identifiers, snapshot field copies and `protected_record`, derived caches/exports/logs and backups. A private snapshot still contains shared text and identifiers; a sanitized statement or hash can remain personal data. Remove covered content and identifying links from every controlled copy under an approved deletion plan. Define backup expiration and deletion replay on restore; disclose and handle external export limits. Do not retain fingerprints, raw requests, source text, participant IDs or full snapshots in an audit tombstone by default.

Retain only justified audit fields, for example a non-identifying event reference, coarse completion time, operation/result and authorization decision reference, with separately restricted access and a fixed approved retention period. Even opaque references and authorization records require reidentification assessment, minimization and expiry. Legal holds require explicit legal authority, narrow segregation and review; a hold is not successful erasure. Exclude evidence from current use while a deletion request is verified/processed under an authorized hold. A terminal tombstone must prevent retry/restore resurrection without retaining prohibited identifying data; this design conflict is unresolved and blocks erasure implementation. After erasure, report deletion completion, never a fabricated valid historical attestation.

## Open security decisions and smallest safe next step

1. Who issues/revokes administrative and privacy grants, where is independent actor identity verified at the SQL boundary, and can an owner ever approve their own case? Decide whether destructive erasure requires two people. Fail closed until approved.
2. How will owner withdrawal be bound to the verified end-user at the database boundary despite service-role execution? A server-derived owner parameter alone does not resist a compromised executor.
3. What initial lifecycle policy covers existing/historical evidence, and how are current canonical checks made without weakening B4.2 fail-closed completeness? No historical backfill is authorized here.
4. What additive event/replacement schema reconciles existing uniqueness/FKs, locks and privacy deletion without weakening immutable history? Which changes to source consent/classification suspend use, and who may clear them?
5. What legal basis, retention durations, hold authority, backup/export policy and non-identifying anti-resurrection mechanism govern erasure? Do not invent retention periods in code.
6. Does the existing trusted promotion credential assumption remain acceptable? Independent administrative authorization does not fix the existing service-role semantic qualification gap.

**Recommendation:** GO for a narrowly scoped owner-withdrawal implementation design after decisions 2 and 3 are approved: private append-only withdrawal authority plus consistent eligibility filtering, authorization and disposable database tests. Keep administrative commands, reactivation, replacement, merge reconciliation and erasure disabled. The implementation must solve end-user binding and compatibility before exposing a command; a deny-by-default event schema alone does not make withdrawal safe. NO-GO for a general lifecycle implementation or any revocation/erasure endpoint until independent authorization and privacy decisions are resolved. This PR authorizes no migration execution, merge or deployment.
