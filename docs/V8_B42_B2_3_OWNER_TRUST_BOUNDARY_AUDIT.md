# B4.2-B2.3 — Owner identity trust-boundary audit

**Decision: NO-GO for enabling owner withdrawal.** The proposed user-token PostgREST boundary is useful against caller-supplied identity and direct service-role execution, but independent owner authorization is not demonstrated. The same project's Auth administration authority creates a credible path to obtaining a genuinely signed owner token. Signature verification cannot distinguish that token from an owner-initiated session.

Audited 2026-10-16 against GitHub main `5b0154312ec0b4b1c77dea0cfa9e0f3fbfcd2936`, the verified merge commit for PR #219. All existing local tracked file blobs were compared with that GitHub tree and matched; the two B2 design documents were fetched at that SHA. This is an offline source audit plus public platform-documentation review, not a deployed-configuration attestation. No project credentials, production/staging, database connections or live authentication experiments were used.

## Authentication and persisted ownership trace

1. [Browser client](../app/supabase.js) uses the public project URL/publishable key. [Login](../app/login/page.tsx#L36) offers signup, password login and OAuth. [Recovery](../app/reset-password/page.tsx#L19) requests a recovery email; [password update](../app/update-password/page.tsx#L35) calls Auth with the browser session. [Callback](../app/auth/callback/page.tsx#L14) reads that session.
2. [validationRequest](../components/validation/api.ts#L5) retrieves the browser session and sends its access token as an Authorization bearer token. Client storage and fields are untrusted.
3. [requireUser](../app/api/_utils/auth.ts#L16) rejects a missing/empty bearer token, creates a public-key client, calls `auth.getUser(token)` and rejects errors/missing users. It does not trust a decoded body/header subject. It delegates token acceptance to Supabase Auth; it does not independently pin JWT issuer/audience/algorithm, require recent authentication or check MFA assurance.
4. [validationHandler](../lib/validation/server/http.ts#L8) authenticates first, then constructs a service-role repository and supplies `user.id`. [Promotion route](../app/api/validation/promotions/route.ts#L4) follows this path. [Service](../lib/validation/server/service.ts) validates the body; [rejectAuthorityFields](../lib/validation/server/contracts.ts#L25) rejects top-level owner fields. Arbitrary context JSON is not an authorization source; not every possible claim name is rejected, but unused claims do not become identity.
5. [Admin construction](../lib/supabase/server-admin.ts#L18) uses `SUPABASE_SERVICE_ROLE_KEY` for the same project. `server-only`, disabled persistence and disabled refresh prevent accidental browser/session use; they do not reduce the credential's remote privileges. The verified user token is **not** carried into the database call.
6. [Repository](../lib/validation/server/repository.ts#L13) scopes owned lookups by both ID and owner; [promotion reads](../lib/validation/promotion/read-repository.ts#L61) scope private source data by owner. [Promotion service](../lib/validation/promotion/promotion-service.ts) prepares evidence and invokes the RPC with `p_owner_id: ownerId`.
7. Database request identity is therefore the service role, not the browser owner. [Latest promotion RPC](../supabase/migrations/20261008010000_qualified_evidence_snapshot_v2.sql#L85) is SECURITY DEFINER, owned by postgres, executable by service_role and revoked from PUBLIC/anon/authenticated (lines 627–635). Its owner checks compare persisted rows with `p_owner_id`; they do not authenticate that parameter using `auth.uid()`.
8. [Ledger composite foreign keys](../supabase/migrations/20260913000000_validation_evidence_promotion_foundation.sql#L31) bind owner to observation, classification, experiment/version/hypothesis/subject, participant and session. Owner is the workspace account, not the interview participant. These constraints establish lineage consistency, not proof that the owner authorized an action.

## Concrete attack paths and mitigations

| Path                                                                 | Evidence, limit and required mitigation                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Service credential → Auth admin → owner session → user-token RPC     | Supabase documents [generateLink](https://supabase.com/docs/reference/javascript/auth-admin-generatelink) for magic/recovery links and [verifyOtp](https://supabase.com/docs/reference/javascript/auth-verifyotp) for verification. A credential holder obtaining a usable owner link/token could redeem it and present an authentic owner JWT. Link generation is not itself a session; whether redemption succeeds under project controls is **NOT VERIFIED**. Isolate the accepted owner proof from Auth-admin issuance/recovery. |
| Service credential → change account access → ordinary login/recovery | [updateUserById](https://supabase.com/docs/reference/javascript/auth-admin-updateuserbyid) supports password/email changes without the normal confirmation flow. [Admin factor deletion](https://supabase.com/docs/reference/javascript/auth-admin-deletefactor) removes MFA factors. These are documented platform capabilities; exact project effects remain **NOT VERIFIED**. Ordinary same-project MFA/AAL or recent-login claims alone do not prove isolation: assess reset, deletion, re-enrollment and recovery too.          |
| Service credential → direct privileged RPC with victim owner         | Existing promotion RPC accepts `p_owner_id` and can read private lineage under definer privileges. It performs real persisted checks but trusts preparation semantics and caller owner selection. Do not give that RPC, its executor or any service-callable wrapper lifecycle-write authority. Preserve B2.2's independent command boundary.                                                                                                                                                                                        |
| Browser → owner/role/sub substitution                                | Body fields or custom headers cannot manufacture a signed JWT. Existing HTTP owner derivation resists this narrow substitution. Future withdrawal must accept only target/revision/request ID, forward the original user proof via a separate public-key client, derive actor from verified gateway context and match persisted lineage. Never convert a service credential into an owner assertion.                                                                                                                                 |
| SQL access → request-claims GUC substitution                         | `auth.uid()` reads trusted request context; it is not a signature verifier. A privileged SQL session able to set that context can impersonate its subject. Do not expose arbitrary SQL, role switching, claim-setting helpers or privileged wrappers to runtime callers. Audit effective catalogs, not only migration text.                                                                                                                                                                                                          |
| Signing/admin authority → accepted claims or policy replacement      | Possessing a service-role JWT is not possession of its signing secret; arbitrary subject editing breaks its signature. Shared signing-secret access is a separate threat. Asymmetric verification limits private-key exposure but does not stop an authorized Auth issuer from issuing an impersonated token. Database/schema administrators can replace local guards; protect the authorization decision and its verification beyond that administrator's control if this actor is in scope.                                        |

Supabase's [API-key documentation](https://supabase.com/docs/guides/getting-started/api-keys) distinguishes API credentials from user identity and explains service_role/BYPASSRLS and object grants. Variable naming does not prove whether this deployment uses a legacy JWT key or a newer secret key; no value was inspected. Neither a key-format change nor a TypeScript wrapper proves least privilege.

Local [Auth configuration](../supabase/config.toml#L165) does not establish a pinned asymmetric issuer; it includes disabled TOTP/phone enrollment and verification (lines 297–309), disabled email confirmations and secure password change (lines 226–228). These are local development settings, **not findings about production**. No application withdrawal step-up was found.

## B2.2 evaluation and smallest secure change

B2.2's user-token PostgREST design can enforce signed-context actor derivation, owner/target matching, generic cross-owner errors, authenticated-only EXECUTE and narrowly scoped atomic writes **against ordinary API callers**, if implemented and tested with real gateway verification and effective SQL grants. None of those requires trusting an HTTP owner parameter. It cannot establish that the same Auth administrator did not obtain that user token, nor resist a database administrator replacing its function.

The smallest defensible architectural change is a **separate owner authorization credential boundary**, not merely another client:

- Remove Auth-admin-capable credentials from the application executor where possible, replacing data access with narrowly scoped database execution. A second key for the same unrestricted service role is not separation. Any administrator retaining owner recovery/issuance authority remains inside the threat boundary.
- If same-project Auth cannot exclude the service/backend administrator, require an independently verified owner-held factor or independent issuer. Enrollment, subject-to-persisted-owner mapping, key rotation and recovery must be inaccessible to that actor. Bind a fresh, short-lived, single-use authorization to owner, promotion, withdrawal operation, revision, request ID and audience; enforce replay protection.
- A separate issuer is one implementation option; independent step-up can suffice only when its verifier, enrollment and recovery have the required separation. Same-project MFA, app_metadata roles, email confirmation or an app-service-issued grant are insufficient evidence by themselves.
- Enforce this proof at a protected gateway/executor and use a dedicated NOLOGIN definer with minimal grants and a fixed pg_catalog-first search path. Revoke service-role/direct/wrapper lifecycle writes. If database administrators are also adversaries, an external authoritative authorization/event record and independently enforced consumption boundary are necessary: a signature checked solely by SQL they can replace is insufficient. Do not claim the database is administrator-proof.

**Smallest next PR justified:** a disabled authorization-proof contract and disposable verification harness for the selected independent boundary, with protected enrollment/recovery and subject binding explicitly specified. Demonstrate signed owner intent, replay/cross-target rejection, and inability of the application credential/Auth administrator to obtain accepted proof. Do not add withdrawal execution yet. Issuer/factor selection and the precise administrator threat model need review before that implementation; this audit does not authorize an architectural rollout.

## Remaining external verification gates

In a separately authorized disposable environment only:

1. Pin the intended Auth/gateway versions and configuration. Verify admin link issuance/redemption, password/email changes, factor deletion/re-enrollment and recovery using synthetic accounts; document whether any yields a token accepted by the proposed boundary. Confirm algorithms, issuer, audience, expiry, assurance and legacy-key acceptance. Do not experiment on real owners.
2. Prove credential separation and protected enrollment/mapping/recovery using the actual selected issuer/factor. Test compromised application credentials, Auth admins, forged/expired/wrong-audience tokens, copied claims and replay. If trusted infrastructure operators are excluded, explicitly record that limitation rather than implying independence from them.
3. Apply the complete migrations to a disposable database and inspect effective role memberships, schema rights, default/explicit table and function privileges, overloads, SECURITY DEFINER owners/search paths and every service-callable wrapper. Test real PostgREST token verification; SQL SET ROLE/GUC fixtures alone cannot prove it.
4. Before enabling withdrawal, pass B2.2's lifecycle/integrity/concurrency/current-read matrix, including all polarities, missing historical authority and no fallback/backfill. Those capabilities remain unimplemented.
