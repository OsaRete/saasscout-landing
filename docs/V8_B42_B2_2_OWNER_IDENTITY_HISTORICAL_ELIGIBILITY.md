# B4.2-B2.2 — Owner identity and historical eligibility

Status: proposed decisions for review; documentation only. No withdrawal capability or security guarantee is implemented by this document.
Baseline: GitHub `main` at `6d9284d6559586da0a8e307a0e7e7a9c11d09194`, including merged PR #218.
The [B2.1 lifecycle contract](V8_B42_B2_1_VALIDATION_LIFECYCLE_CONTRACT.md) remains authoritative.

## Verified implementation facts

- [Authentication](../app/api/_utils/auth.ts) calls Supabase Auth `getUser(token)`. The [Validation handler](../lib/validation/server/http.ts) then creates an admin client and passes `user.id` to services. The [promotion service](../lib/validation/promotion/promotion-service.ts) supplies `p_owner_id` to a service-role-only RPC. SQL verifies persisted lineage and preparation freshness, but does not independently authenticate that owner.
- The [domain schema](../supabase/migrations/20260828000000_create_validation_domain.sql) permits authenticated SELECT through `owner_id = auth.uid()` RLS and denies authenticated writes. The [promotion ledger](../supabase/migrations/20260913000000_validation_evidence_promotion_foundation.sql) binds owner, observation, classification, experiment lineage, participant and interview session through composite foreign keys. Owner means the Validation workspace owner, not the interview participant.
- The [integrity migration](../supabase/migrations/20261008000000_qualified_evidence_integrity.sql) restricts runtime ledger/snapshot access to service-role SELECT and guards attested shared rows. The [v2 migration](../supabase/migrations/20261008010000_qualified_evidence_snapshot_v2.sql) atomically attests new promotions using the native whole-row codec and exact protected schema. Exact promotion retries return the existing result without attesting history.
- The [trusted reader](../lib/validation/promotion/trusted-qualified-evidence-reader.ts) validates the B3.1 fingerprint and v2 proof in one PostgREST SELECT, caps candidates at 100, requires exact completeness and returns eight allowlisted fields. Otherwise qualifying rows with missing, v1, unsupported or corrupt integrity fail the whole read generically. It has no lifecycle or current canonical-status check.
- [Canonical resolution](../lib/validation/promotion/canonical-resolution.ts) uses active registry entries during preparation; that is not a current-read guarantee. [Internal tester access](../lib/auth/user-capabilities.ts) grants scan capabilities, not owner impersonation or lifecycle administration.

These are source-code facts, not verification of deployed Auth settings, JWT signing keys, role memberships or production grants. No database was accessed.

## Decision: a user-token withdrawal RPC, with an explicit trust prerequisite

Use a new PostgREST RPC, conceptually
`validation_withdraw_qualified_evidence(p_promotion_id uuid, p_expected_revision bigint, p_request_id uuid)`.
No owner, actor, role, canonical choice or approval parameter is accepted. This operation only withdraws shared use; it neither deletes proof nor declares qualification false.

1. Require an end-user access token verified by the PostgREST authentication gateway against a pinned trusted issuer, audience and asymmetric verification keys, with expiry and the approved authenticated role. The HTTP handler may retain `requireUser`, but must forward the original user token through a separate user-scoped client, never the admin client. Do not exchange the service credential for a user assertion.
2. Inside SQL, require the gateway's authenticated request role and a non-null UUID `auth.uid()`; derive the actor exclusively from that verified context. Do not use `current_user` inside a SECURITY DEFINER function to identify the caller. JWT/session GUCs are gateway assertions, not database-verified signatures: arbitrary SQL access that can set them is outside this boundary and must not be available to runtime callers.
3. Select the final ledger by both promotion ID and derived actor. Recheck its owner-bound observation, classification, experiment/version, subject, participant and session lineage using persisted keys in the transaction. Reject missing/inconsistent lineage. Do not infer ownership from shared text, metadata, a browser ID or a supplied source record. Preserve existing proof and polarity.
4. Acquire B3.1 coordination locks in canonical-registry → sorted experiments → participant → representative-group order, then the promotion lifecycle lock; re-read authority after locking. Allow only B2.1 `active`, `suspended` or `pending reconciliation` → `withdrawn`, or an exact authorized retry. Missing lifecycle authority is an error, not an implicit initial state.
5. Atomically append one owner-withdrawal event and advance the eligibility revision. Bind the event to the derived actor and persisted promotion owner, with database time and a fixed reason code. No free-form private source content is needed. A retry with the same actor/request/payload returns the prior acknowledgement even if its expected revision is now old; reuse with different payload fails. Other stale revisions fail. Withdrawal cannot reactivate in place or weaken a stronger restriction.

### Required SQL privileges and RLS

- Own the SECURITY DEFINER RPC with a dedicated NOLOGIN role, not an application login. Give it only necessary lineage SELECT, lifecycle INSERT and guarded projection UPDATE privileges. Use a fixed `pg_catalog`-first search path and schema-qualified objects; no dynamic SQL or caller-selected functions.
- Revoke RPC EXECUTE from PUBLIC, anon and service_role; grant only to authenticated. Audit inherited memberships, overloads, default privileges and callable wrapper functions so no service-role route can invoke it. Retain the in-function role check as defense in depth.
- Keep ledger/snapshot private: no new authenticated SELECT grant. Enable RLS on new private lifecycle tables with no runtime direct-write policy. Revoke all direct INSERT/UPDATE/DELETE/TRUNCATE from runtime roles, including service_role; permit writes only through narrowly privileged functions. Enforce append-only events independently of RLS. If a projection is mutable, only the internal transition function may advance it.
- The function deliberately accesses private lineage using its definer privileges, so explicit actor/owner predicates are mandatory; RLS alone does not authorize the command. Any future owner receipt SELECT must separately enforce `owner_id = auth.uid()`; this design needs only an RPC acknowledgement.
- Return the same generic not-found response for absent and other-owner targets, before exposing lifecycle state or retry results. Return only the caller's minimal acknowledgement. Never expose private joins, owner IDs, snapshot contents, raw SQL errors or cross-owner counts in responses/logs. Authenticate before target lookup; scope idempotency lookup by actor.

### What service_role resistance can actually mean

At the proposed PostgREST boundary, a service-role token cannot execute withdrawal, and adding an owner ID, forged claims header or `sub` body field cannot turn it into a signed owner token. RLS BYPASSRLS does not grant EXECUTE or table privileges. However, this is **not yet a justified end-to-end guarantee for the existing deployment**.

The inspected code does not establish whether possession of `SUPABASE_SERVICE_ROLE_KEY` also permits Auth-admin session/link issuance or other account takeover paths. Asymmetric signing alone does not eliminate an Auth-admin impersonation path. Nor can `auth.uid()` resist a privileged SQL login that sets request claims, a shared JWT signing secret, or a database administrator changing guards.

**Required minimal architectural change:** replace service-executed withdrawal with the verified user-token PostgREST boundary above, and isolate owner-token issuance/recovery from the application service credential. Before enablement, prove that this credential cannot mint, obtain or reset an owner's accepted token. If the existing Supabase Auth administration model cannot provide that isolation, use a separate owner authorization issuer with an independent user-verification/step-up factor and protected enrollment/recovery; accept only that issuer's owner assertions at a dedicated gateway role. Its subject-to-owner mapping must be protected from service-role writes. A server-derived actor parameter or a service-issued grant is not a substitute.

Issuer selection, protected subject mapping and demonstrated credential isolation remain an **enablement blocker**. Until resolved and tested, expose no withdrawal endpoint. This design does not repair B2.1's separate trusted-promotion semantic gap or defend against database/schema administrators.

## Decision: conservative historical compatibility

Historical integrity, lifecycle authority and current canonical permission are separate predicates. Never derive active status from finality, `eligible = true`, age, a valid fingerprint or a v2 snapshot.

| Evidence condition                                                                       | Future lifecycle-aware current-read treatment                                                                                                                                                                                                                                                 |
| ---------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Final historical promotion without lifecycle authority, including valid v2               | Zero eligible contribution; fail the complete requested read with a generic authority error. Do not silently skip it, manufacture an exclusion event or label it persisted pending reconciliation.                                                                                            |
| Otherwise qualifying promotion with missing, corrupt, v1 or unsupported integrity/schema | Fail the complete read under existing B4.2 rules. No re-attestation, codec downgrade or retry repair. A lifecycle label must not hide this failure.                                                                                                                                           |
| Valid existing v2 snapshot                                                               | Preserve as supported historical proof unchanged. It establishes no consent renewal or active lifecycle authority. If separately authorized lifecycle authority ever exists, evaluate it using the same proof rules as new evidence. No activation path for historical rows is included here. |
| Explicit, valid non-active lifecycle authority                                           | Exclude from current evidence/counts without rewriting historical proof. Validate the exclusion's target, event chain and revision; for this owner-withdrawal scope still validate supported integrity. Erasure exceptions remain outside scope.                                              |
| Explicit active authority plus valid proof                                               | Include only if the exact persisted canonical UUID is currently permitted in the same database snapshot; preserve supporting, contradicting or mixed polarity.                                                                                                                                |

Current canonical eligibility requires the exact UUID to exist and remain active, with no authoritative merged/deprecated/ambiguous identity condition. Do not follow aliases to another UUID or rewrite old titles/fingerprints. A same-UUID rename alone does not invalidate historical proof. Where current schema cannot establish unambiguous identity, fail the complete read; future reconciliation authority is required. Canonical ineligibility restricts use immediately even before a background event exists; it must not fabricate a persisted lifecycle event.

No automatic activation, historical reclassification, initial-event backfill or snapshot backfill is authorized. New promotions may receive an initial active event only atomically with qualification, shared row and supported attestation in a future implementation. Existing promotion retries remain duplicates and never create initial lifecycle authority. Historical withdrawal without initial authority stays blocked pending a separately reviewed historical restriction policy; do not invent a state transition.

**Compatibility boundary:** leave the existing trusted reader unchanged until the lifecycle-aware implementation is ready, and keep new consumers disconnected as B2.1 requires. It remains a historical integrity reader, not proof of current permission. Before enabling withdrawal, atomically switch all designated current readers/counts to one consistent PostgreSQL/PostgREST authority read; never fall back to the old reader on failure. Preserve candidate completeness/cap handling and the eight-field output. Missing authority in a mixed population fails the whole read, not a partial subset presented as complete. Fail closed does not mean returning a successful empty evidence set.

## Minimum future implementation surface

- Add private, versioned append-only lifecycle events and a uniquely keyed current revision/projection per promotion, bound by composite `(promotion_id, owner_id)` FK to persisted ledger lineage. Store event ID, predecessor/revision, actor, fixed operation/reason, request ID and database timestamp. Enforce one successor per revision and actor/request idempotency with payload equality. Projection/event disagreement fails closed.
- Add only the owner withdrawal RPC and its user-token HTTP adapter, grants and generic error mapping described above. Implement no administrative, privacy, replacement or reactivation command.
- Extend controlled promotion atomically to create initial lifecycle authority for genuinely new evidence; preserve duplicate fast paths, uniqueness and existing ranking/qualification behavior.
- Add a server-only current-read SQL boundary that evaluates candidate completeness, supported integrity, lifecycle revision and exact current canonical authority in one consistent statement snapshot. Multiple READ COMMITTED RPC statements are not automatically one snapshot: use a single SELECT/CTE authority evaluation, or explicitly proven transaction isolation. Keep raw private authority out of consumer output.
- Coordinate canonical writers and lifecycle transitions with existing lock order. A read linearizes at its SQL snapshot: one started before withdrawal may see the prior state; any snapshot acquired after withdrawal commits must exclude it. No cache or count path may restore stale eligibility.

These are requirements for a future PR, not migrations or API implementations in this PR.

## Remaining decisions and scope

GO for review of this bounded design; NO-GO for endpoint enablement until owner-token issuance/recovery isolation and database role assumptions are proven. Historical activation/restriction enrollment remains separately designed and disabled; accepting this conservative policy may make a canonical's current read unavailable while historical authority is missing.

B2.1 administrative grant issuance, privacy/retention/erasure, replacement and broader canonical reconciliation decisions remain unresolved and disabled. No application code, SQL migration, lifecycle endpoint, historical backfill, Knowledge Evolution integration, merge or deployment is included.
