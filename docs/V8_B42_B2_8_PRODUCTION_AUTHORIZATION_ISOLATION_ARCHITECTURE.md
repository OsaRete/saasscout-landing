## 2. Decision and deployment options

Recommend **a small external authorization service with an owner confirmation origin, protected registry, and narrowly privileged database executor**. Keep Next.js and ordinary Supabase authentication for workspace access. Require an independently enrolled owner-held key for destructive owner intent. Initially support only synthetic verification; later stages remain disabled until separately reviewed.

| Option                                                                                    | Guarantees and trust assumptions                                                                                                                                                                | Infrastructure, cost and operations                                                                                                                                                                                                                                     | Implementation/testing                                                                                                                                                   |
| ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Separate Vercel project or Supabase Edge Function under existing administration           | Can separate runtime secrets from ordinary application execution. Shared organization admins, CI secrets or Supabase project administrators can replace verification; not independent from them | Lowest additional hosting cost; existing platform tooling; still needs durable registry and replay                                                                                                                                                                      | Easiest packaging, but effective admin/Auth/grant tests remain necessary. Suitable only if shared administrators are explicitly trusted                                  |
| **External managed container service in a separately administered cloud account/project** | Application credentials cannot read registry, sign receipts, recover keys, redeploy service or impersonate its workload. Database remains a trusted enforcement root                            | One small service, managed PostgreSQL registry, secret manager/KMS and audit sink; HTTPS/domain/monitoring/backups. Low traffic compute may be modest; managed DB minimums, logs, backups and operator time dominate. Obtain provider/region quotes before provisioning | Moderate: small service and existing PostgreSQL skills; real IAM denial tests, crash reconciliation and SQL privileges require work. Recommended incremental boundary    |
| External authorization plus external authoritative lifecycle/event enforcement            | Can detect database tampering and exclude it when every consumer independently verifies external authority. Still trusts external administrators and consumer infrastructure                    | Additional event store, delivery/reconciliation, independently protected consumers and operational ownership; highest recurring and engineering cost                                                                                                                    | Hardest: distributed consistency, rollback/restore and consumer bypass testing. Required if database administrators must be adversaries; defer for this small-team scope |

A separate account is useful only with separate control: distinct administrator identities, MFA, secret access, CI deployment approvals and break-glass policy. Application maintainers must not be able to approve/deploy verifier changes, change DNS/TLS for its confirmation origin, assume its IAM role, read its backups or use an inherited organization administrator account. The initial verifier may share a runtime with its narrow executor: both are inside the same trusted authorization boundary. Keep lifecycle administration in a separately authenticated control plane, not the application relay API.

**Current infrastructure cannot establish independence from its existing all-powerful owners.** If the same person retains unrestricted application, verifier, Supabase and cloud administration, only runtime credential separation is achievable. Independent administrative control needs another accountable custodian or separately governed provider. Do not relabel two accounts controlled by one unrestricted operator as administrator independence.

### Credential allocation

| Component                 | Permitted credentials/capabilities                                                                                          | Explicitly absent                                                                                                            |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Next.js application       | Existing workspace/Auth capabilities during transition; bounded verifier relay identity with submit/status only             | Owner private keys; registry/recovery writes; verifier deployment/KMS access; executor database login; lifecycle DML/EXECUTE |

| Authorization service     | Registry read, atomic intent reservation, dedicated executor login, workload identity for receipt signing                   | Supabase service_role/Auth-admin key; general application data writes; recovery approval issuance                            |

The application's service_role is not accepted as owner proof or as the executor identity. Audit all service-callable wrappers and effective grants to prevent bypass. Removing broad application service credentials over time is desirable, but the new boundary must remain safe even while that credential exists.

## 3. Independent enrollment, recovery and key revocation

Use WebAuthn on a dedicated origin controlled by the authorization custodians. This is a new production protocol, not a claim that POC Ed25519 keys are WebAuthn credentials. Pin RP ID/origin, allowed algorithms, user verification and challenge handling; test authenticator compatibility. Hardware-backed versus synced passkeys have different recovery trust roots; initially require a hardware authenticator plus a second independently enrolled backup. Do not infer hardware custody merely from a WebAuthn assertion.

For new workspaces, establish the external owner subject and enroll keys before protected evidence is created; bind that subject to the exact workspace owner UUID through an independently approved registration. For existing owners, an Auth session, matching email, billing lookup or application-provided UUID is insufficient bootstrap proof. Require a pre-existing independent organizational identity attestation or documented manual verification using previously established external contacts and two authorization custodians. If that independent evidence does not exist, enrollment is unavailable. Manual judgment remains a stated trust assumption; this document does not magically prove historical ownership.

Enrollment flow:

1. Authenticate directly to the protected owner origin, using independent identity proof; a Supabase session may locate an account but cannot authorize enrollment.
2. Show the exact workspace and proposed key binding; generate a single-use expiring server challenge bound to external subject, workspace UUID, purpose, proposed credential and registry version. Complete registration and fresh proof of possession before activation.
3. Control plane validates the independent decision and possession proof, performs compare-and-set registry activation and appends audit history atomically. Application-supplied IDs are lookup hints only; conflicting mappings fail. Never remap an enrolled external subject through application account recovery, UUID reuse or email changes.

Owner rotation requires current-key user-verified intent plus replacement-key possession, exact fingerprint/credential ID, current registry epoch and a separate rotation domain. Revoke the predecessor permanently; never resurrect it. Backup keys must already have undergone the same protected enrollment. Credential revocation is not Validation evidence revocation and grants no evidence-admin powers.

Lost primary key: use the already enrolled backup to approve a new key on the protected origin. Loss of all keys: require independent re-verification and two distinct custodians, with at least one outside application administration, a documented case and a proposed 72-hour notification/challenge period through pre-established independent channels. The period is policy for review, not identity proof. Application support cannot override it. If independent recovery is impossible, remain locked out; do not use email-only reset, Auth-admin link, service-role approval or an emergency key setter.

Only an independently authenticated recovery request may enter pending recovery; unauthenticated requests cannot suspend an owner. Pending recovery immediately blocks new owner intent and rotation. Freeze unresolved in-flight operations until reconciled. Completion revokes lost keys, advances epoch, activates a distinct proven replacement and records reviewers/decision. Disputed cases stay blocked. Key compromise can trigger independently authorized suspension/revocation without replacement; availability loss is safer than silent impersonation.

Audit enrollment, failed decisions, rotation, revocation, recovery start/completion/cancellation, epoch changes and privileged access. Record immutable event/predecessor IDs, external actor/reviewer IDs, purpose, fingerprints, expected/resulting epoch, decision/request reference, time and outcome. Minimize identity documents and evidence content; restrict retention/access separately. Commit state and audit together; unavailable audit persistence denies lifecycle changes. Export signed checkpoints to a separately protected retention sink. Hash chains aid detection only while checkpoints remain protected.

## 4. Verifier, requests and durable storage

The owner confirmation page fetches target context directly through the protected service, displays the evidence/shareable statement, exact operation and revision, and requires user verification. Never ask an owner to sign an opaque application-generated challenge. Treat the main application as potentially malicious: it may relay or suppress requests but cannot change what the trusted confirmation origin displays. Compromised owner devices or the confirmation origin remain risks.

Production intent needs a new versioned canonical schema: deployment/project audience, independent owner subject and mapped workspace UUID, promotion UUID, operation `withdraw`, expected lifecycle revision, registry epoch/credential ID, request ID, server challenge, issued/expiration times and digest of displayed immutable evidence context. Use an unambiguous codec and domain separation; reject unknown/duplicate fields and unsupported versions. Maximum validity is five minutes with exclusive expiration, bounded clock error and monitored time. WebAuthn challenge binds the hash of these exact bytes; verify RP/origin, challenge, signature, user verification and enrolled credential against protected state. Do not reuse the POC's overloaded rotation fields or accept request-selected algorithms/public keys/URLs.

Application relay traffic uses authenticated HTTPS with a rotated dedicated client identity, strict request limits, rate limiting and generic cross-owner errors. This identity authorizes submission only. Direct owner sessions need protected-origin cookies, CSRF defenses and origin checks. Authenticate executor-to-database connections with TLS verification and a separate database login stored only in the verifier account; use restricted network paths where supported. No general production database credentials go to application preview builds or CI.

Store owner registry, epochs, single-use challenges, pending intents, lifecycle decisions and audit in managed PostgreSQL under verifier-account IAM. No application network/database access. Separate verifier read/reservation privileges from control-plane registry mutations. Encrypt backups, restrict restore/delete privileges and test recovery. Receipt/checkpoint signing uses a non-exportable KMS key with an explicit algorithm allowlist; key IDs and rotation overlap are pinned by consumers. Owner keys never enter that KMS. KMS limits extraction, not an authorized compromised workload signing false assertions.

Use durable unique constraints on challenge IDs and `(deployment, request_id)`, payload hashes and compare-and-set status transitions. Concurrent submissions across replicas reserve one logical intent. Invalid attempts do not consume a legitimate challenge. Persist reservation before dispatch; store a stable request and exact payload for retries. Never report operation success merely because a signature verified. Status is `pending`, `committed`, `denied` or `indeterminate`, with no pending-as-success response.

Verifier outage, unknown registry state, revoked key, pending recovery, time uncertainty, storage error, unsupported proof or unavailable executor denies new authorization. No fallback to service_role, cached approval, same-project MFA or a boolean. A lost response is indeterminate until authenticated status reconciliation; never instruct a blind new operation. Already committed withdrawal stays effective without verifier availability. Read outages must not restore old eligibility.

## 5. Supabase consumption and transaction boundaries

Recommend direct execution by the protected service through a dedicated PostgreSQL login, rather than application consumption of a transferable approval receipt. This refines B2.2's proposed user-token-only RPC: workspace login remains useful, but cannot supply independent authority. Receipt signatures are audit/acknowledgement material, not permission for an application service-role RPC. If a later design transports receipts through the app, SQL must cryptographically verify exact claims with pinned keys and atomically consume them; TypeScript verification or an owner/verified flag is insufficient.

The dedicated executor supplies the independently verified external subject/owner binding and canonical signed intent to one fixed function. These are trusted assertions only because the authenticated executor login is inaccessible to the application; SQL does not independently prove the WebAuthn signature in this option. SQL derives the target owner from persisted ledger lineage and requires equality with that protected binding. Owner fields from clients, ordinary JWT claims/GUCs, `internal_tester` and service-role inputs never select authority. A compromised verifier can assert falsely: it remains a trust root.

Required PostgreSQL enforcement:

- A dedicated NOLOGIN function owner with minimal lineage SELECT and lifecycle append/projection privileges. Schema-qualified objects, fixed `pg_catalog`-first search path, no dynamic SQL, no runtime schema CREATE or role switching. Revoke PUBLIC/anon/authenticated/service_role EXECUTE and direct lifecycle DML/TRUNCATE; grant EXECUTE only to the dedicated login. Inspect inheritance, overloads, default privileges, triggers, cascades and every callable wrapper in the actual catalog. BYPASSRLS is not an object-grant override.
- Lock in existing canonical registry → sorted experiments → participant → representative group order, then lifecycle authority. Recheck persisted owner-bound lineage, immutable proof, expected revision, exact permitted transition and current canonical requirements. No owner inference from shared metadata. Missing initial authority, broken chain or projection mismatch fails closed.
- In **one database transaction**, insert unique request consumption with exact payload hash/actor binding, append the withdrawal event, advance projection/revision and write a minimal durable acknowledgement/outbox. Any failure rolls all of these back. Request ID reuse with changed payload conflicts; exact committed retry returns the same acknowledgement without another transition. Distinct IDs racing the same revision have one winner. SQL checks expiration at transition time; a delayed queue cannot extend consent.
- Preserve ledger, snapshot, shared row, canonical UUID/title, fingerprint, human provenance and supporting/contradicting/mixed polarity unchanged. Withdrawal only restricts shared use. No reactivation, evidence revocation, replacement or erasure capability follows from key administration.

There is **no atomic transaction spanning verifier registry and Supabase**. Do not consume locally then assume a separate database write will succeed. Use protected per-owner serialization: verifier execution holds a registry coordination lock from current-epoch validation through the database commit/result reconciliation; all rotation/revocation/recovery paths use that same coordination. Multiple replicas must share the lock. Durable pending state is recorded before dispatch. A control-plane transition cannot complete while an earlier operation is unresolved.

A process/connection failure can release a registry lock while the database transaction still commits. Therefore a successor must first reconcile the exact pending request with the database acknowledgement; if absent, it must prove the prior database attempt terminated before cancelling or changing epochs. Timeouts alone do not prove termination. Until then, block that owner's execution and key transitions. The eventual implementation must test this coordination protocol, including session termination and ambiguous commit, before enablement. This trades availability for safety rather than claiming distributed exactly-once delivery. PostgreSQL uniqueness establishes at most one committed effect; retry reconciliation supplies a stable result. Revocation linearizes after earlier resolved operations; it cannot undo a committed withdrawal.

Backups/restores can roll back replay state. Restore procedures must disable dispatch, reconcile verifier intents and database acknowledgements, and establish a new deployment epoch/audience with fresh challenges before reopening. Never replay old pending proofs into a restored database. Preserve consumed identifiers for the reviewed retention window and maintain non-reusable deployment namespaces; retention/restore sign-off is an enablement gate.

Before enabling any command, implement B2.2's lifecycle-aware consistent SQL current-read boundary for **all designated readers/counts/caches**. Only explicit active authority plus supported integrity and permitted exact canonical identity contributes. Mixed historical populations missing authority fail the whole read generically; never infer active, silently skip unknown authority or fall back to the historical reader. Preserve completeness/caps and eight output fields. Same-UUID rename preserves history; no alias retargeting. Post-commit snapshots exclude withdrawal; an earlier snapshot may see prior state. Define cache invalidation or disable caching so it cannot resurrect eligibility. New initial authority must commit atomically with genuinely new promotions; duplicate retries never backfill it. Historical activation/restriction requires separate policy and remains blocked.

## 6. Threat model and residual risks

| Actor                                           | Intended protection after implementation and testing                                                                                                   | Residual trust/limit                                                                                                                                                |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Untrusted client                                | Cannot forge key possession, choose authority, change signed target or reuse intent; generic errors prevent target disclosure                          | Owner device compromise, phishing/social engineering and denial of service remain                                                                                   |
| Compromised application credentials             | Cannot access protected registry, executor login, KMS or control plane; no lifecycle bypass through SQL grants                                         | Existing application/private-data exposure and malicious promotion semantics remain outside withdrawal guarantee                                                    |
| service_role misuse                             | Auth-admin session/reset is insufficient; direct/wrapper lifecycle execution denied                                                                    | Effective grants and same-project Auth capabilities must be tested with synthetic accounts; credential still has broad unrelated powers                             |
| Malicious/compromised application administrator | Cannot redeploy protected origin/verifier, alter registry/recovery, assume workload or change executor grants **if administration is truly separated** | Can suppress UI/results, steal app data or misrepresent output. Cannot guarantee honest display by a malicious app; designated trusted consumers must enforce reads |
| Compromised verifier administrator              | No guarantee of correct authorization; may change code, registry or use KMS/executor                                                                   | Separate approvals, audit checkpoints and alerts reduce/detect risk, not eliminate it                                                                               |
| Database administrator                          | Cannot necessarily extract external owner keys/registry                                                                                                | Can change SQL/grants/lineage, forge lifecycle state or omit withdrawal. This option trusts DB admins for database effects and current reads                        |
| Infrastructure administrator                    | Application-only infrastructure access is isolated if accounts/CI/DNS are separate                                                                     | Control of verifier hosting, identity, KMS policy, database or organization root defeats relevant enforcement; common root is explicitly trusted                    |

External audits do not make administrator-controlled SQL honest. Resistance to database administrators requires the third deployment option and independently enforced consumers. No guarantee is made against colluding custodians, verifier compromise, compromised external identity providers or infrastructure roots. Recovery identity quality, actual separation staffing, WebAuthn custody choice, SQL connectivity/grants, crash protocol and historical compatibility remain the most important unresolved risks.

## 8. Production withdrawal GO / NO-GO

**Current decision: NO-GO.** GO for review of this architecture and then the disabled codec PR only. Docker success is necessary learning, not a production authorization attestation.

Production GO requires all of the following with linked, reproducible evidence and explicit review:

- Named trust roots/custodians, real separate IAM/CI/DNS/secret control and an accepted statement that verifier, database and infrastructure root administrators remain trusted.
- Independently established exact owner mapping, protected-origin informed consent, key possession/custody and tested recovery/revocation with no unilateral application/Auth-admin override. Owners without independent bootstrap proof remain ineligible.
- Real credential attack tests for application/service_role/Auth admin and internal_tester; protected registry/executor denial, audited effective PostgreSQL grants and no bypass wrappers.
- Durable request uniqueness and atomic lifecycle/acknowledgement rollback, real concurrent connections/replicas, crash/ambiguous commit reconciliation, key-transition ordering and safe backup/restore epoch procedures.
- B2.1/B2.2 current-read, historical, exact canonical, integrity, immutable provenance and all-polarity regressions; all designated readers/counts/caches switched together without fallback or backfill.
- Monitored TLS/time/storage/audit availability, tested fail-closed outages, minimal generic errors, incident response, retention policy, independent review and separately approved migrations/deployment/feature enablement.

Any missing gate is NO-GO. No administrative evidence revocation, privacy deletion, replacement, reactivation, historical activation or Knowledge Evolution is approved. This PR changes only this document and preserves all existing Validation behavior and evidence invariants.
